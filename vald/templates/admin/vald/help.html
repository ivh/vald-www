Approval always comes before activation, never the other way round. Both routes that can set a password — the activation link and the reset link — refuse an account with is_active off, so an unapproved registrant cannot let themselves in by asking for a password reset.

Actions on the user list

The same four actions appear in the changelist dropdown and, where they would have an effect, as buttons at the bottom of an individual user page.

Approve and send activation email
Sets is_active, issues a fresh activation token, mails the link to the primary address. Skips users who are already active, so it will not re-mail an active account — use Clear password first if that is what you want.
Approve without sending email
Sets is_active only — the same edit as ticking Active on the user page and saving, history entry included. The account then sits in Approved, not activated until the holder tries to log in, which mails them a link. Use when you will tell them by other means.
Clear password (force re-activation)
Drops the password and any pending token. Does not deactivate. The next login attempt on that address mails a fresh activation link. This is the way to recover an account whose holder has lost access to it.
Reject pending registrations
Deletes the selected users, but only those in Pending approval. Active or suspended accounts in the selection are left alone, so this cannot destroy a working account by accident.

To suspend a working account, untick is_active on the user page. The password survives, so re-ticking it restores access with no email round trip.

Links and tokens

Activation and password-reset links share one activation_token field per user, valid for {{ token_max_age_days }} day{{ token_max_age_days|pluralize }} from issue. Issuing a new one invalidates the previous link, and setting a password clears the token so a link cannot be replayed. A user who reports a dead link should simply try to log in again, which issues another.

Requests

Queue right now: {{ queue_stats.queue_size }} / {{ queue_stats.max_queue_size }} pending, {{ queue_stats.max_threads }} job thread{{ queue_stats.max_threads|pluralize }}.

A request goes pending → processing → complete, or to failed if the job errored or hit the timeout. pending means queued, processing means a Fortran binary is running. Result files are deleted after {{ retention_days }} day{{ retention_days|pluralize }}; the request row stays and reports its results as expired, which is why an old completed request can show no download.

That is the queue as it stands. For volume over time — requests per day, month or year, who submits most, the split by request type, and how long requests take — see the request statistics page.

The timings there are turnaround: completed_at minus created_at, which is queue wait plus run time. Nothing records when a job actually started, so during a busy spell turnaround rises even though the Fortran is no slower. Read a jump in it as pressure on the queue, not as extractions getting more expensive.

The one marked (default) is what a request gets when it names no other, what a personal configuration is snapshotted from, and what the rest of this page means by “the VALD default”. There is exactly one. The others are alternatives, chosen per request; picking one does not interact with the user's personal configuration.

A submitted request stores the slug, not the label, so renaming a configuration is safe and changing its slug orphans requests that already chose it. default and personal are reserved.

Re-importing

The filename decides nothing. The target is chosen by --slug, or by its absence:

bin/vald-manage import_default_config <file>              # replaces the default
bin/vald-manage import_default_config <file> --slug vald3_all  # replaces that variant

Either way the configuration is rebuilt in place: it keeps its name, slug and identity, its linelist entries are replaced from the file, and personal configurations are untouched. Omitting --config-name keeps the label the menu already shows.

Pointing the wrong file at a slug is silent. Importing VALD3_all.cfg without --slug overwrites the system default with the all-lines set, and every user tracking the default gets predicted lines — while the menu still says “Default”. Nothing objects, and --dry-run will not catch it either: it reports the parse, not the target. Check the Enabled column above after any import; the count is distinctive per file.

Personal linelist configurations

Every user is in one of two states, and the difference decides what their extractions actually use. This is the most common thing users ask about.

Using the VALD default

How They have never edited anything on the Personal Configuration page — merely visiting it does not count.

Effect Their requests use the VALD default, and automatically pick up linelists added in future VALD releases.

Count {{ tracking_default }} user(s)

Personal configuration

How They edited a linelist, took a fresh copy of one of the system configurations, or the account was migrated from the legacy interface.

Effect A snapshot of whichever system configuration they copied — the default unless they chose another — as it was when taken, plus their changes. It does not follow later updates: a new linelist in a VALD release does not reach them.

Count {{ personal_total }} user(s), of which {{ personal_behind }} {{ personal_behind|pluralize:"is,are" }} missing at least one linelist that the configuration they copied has now. Each is measured against its own source, so a copy of a variant is not counted as behind the {{ default_linelist_count }}-linelist default.

Do Nothing, usually — a snapshot is a deliberate choice, and stability is often what the user wants. The Personal Configuration page tells them what they are missing and offers to remove it.

To see a specific user's configuration, open them from the user list and follow the Configuration link, or use the column on the list itself. It is read-only and shows only the entries that differ from the configuration that user copied, which is usually a handful out of several hundred.

Their three buttons, and what each means:

Save (on any linelist row)
Creates the personal configuration if they had none. This is the moment they stop tracking the VALD default.
Remove personal configuration
Deletes it. They go back to tracking the default and pick up everything added since. Their changes are lost — there is no undo.
Take a fresh copy (with the configuration menu beside it)
Replaces it with a fresh copy of the chosen system configuration as it is today, discarding their changes. They stay frozen, just at a newer starting point — and possibly on a different base, which is what Config.snapshot_of records.

The date shown on a configuration is when it was taken, not when the database row was written. For the accounts migrated from the legacy interface that is the old .cfg file's timestamp, often years back — which is exactly how far behind the current default they are.

Rank weights run 0–9, not 1–9: the shipped default.cfg uses 0 on a number of entries. Values outside that range are pinned to it when edited here, but configurations imported from legacy files are carried across verbatim, so an occasional out-of-range value from the old system survives.

Retiring a linelist

Leave it out of default.cfg and re-import: 

bin/vald-manage import_default_config $VALD_HOME/CONFIG/default.cfg

The importer deactivates any linelist that is then in no system configuration, and generated configurations skip inactive ones. That is what stops a years-old personal snapshot from naming a data file that has left the SVN tree. A linelist that reappears in a later import is reactivated.

Note the scope. A list dropped from default.cfg but still present in one of the other configurations above stays active, so to retire it properly remove it from all of them. The union is deliberate: the VALD3_all variants carry predicted-line lists default.cfg does not, and judging one file at a time would have each import retire whatever the previous one added.

Deploying a new version

All of this runs on the server as the vald user, from {{ base_dir }}. Steps 5–6 are only needed when the unit files themselves changed; the rest apply to every deploy.

  1. Snapshot the database first. 
    sudo systemctl start vald-backup.service
    The nightly timer does this too, but a migration is the one thing worth having a fresh snapshot before. Snapshots are tagged with the git revision, because a dump only restores against a codebase at a compatible migration state. Start the unit, not scripts/backup_db.sh directly: the script defaults to backups/ inside the checkout, while the unit sets VALD_BACKUP_DIR to where the nightly snapshots actually go. Running the script bare puts the one snapshot you care about somewhere you will not look for it.
  2. Pull the code, and sync dependencies if they changed. 
    git pull
uv sync
    Dependencies are pinned in uv.lock; uv sync makes .venv match it exactly.
  3. Apply migrations. 
    bin/vald-manage migrate
    Use bin/vald-manage, not python manage.py. manage.py defaults to the development settings module, whose VALD_HOME and result directory point somewhere else entirely; the wrapper reads secrets.txt and sets DJANGO_SETTINGS_MODULE=vald_web.settings_deploy. This instance is running {{ settings_module }}.
  4. Collect the static files. 
    bin/vald-manage collectstatic --noinput
    Easy to skip, and it fails quietly: the browser keeps serving the old stylesheet, so a CSS change looks like it had no effect while a template change in the same commit appears immediately. Nothing is served from style/ at runtime — the web server serves the staticfiles/ snapshot this command writes, and only this command updates it.
  5. If any unit file changed, copy it into place: 
    sudo cp {% for name in unit_files %}{{ name }} {% endfor %}/etc/systemd/system/
  6. ...and reload systemd, which is what makes a changed unit file take effect. Restarting alone will not. 
    sudo systemctl daemon-reload
  7. Restart the application. 
    sudo systemctl restart vald
  8. Check it came back. 
    systemctl status vald
journalctl -u vald -n 50

First-time setup only, to arm the scheduled jobs: 

sudo systemctl enable --now vald-cleanup.timer vald-backup.timer
Verify with systemctl list-timers 'vald*'.

Things that surprise people

There is no collectstatic step
Static files are served by the reverse proxy directly from the checkout. STATIC_ROOT is declared but unused.
Some deploys sign everyone out
Sessions are revalidated against the database on every request, so a change to how they are keyed invalidates existing ones. Changing VALD_URL_PREFIX does the same, because the session and CSRF cookie paths derive from it. Harmless, but expect the support email.
A restart kills running extractions
Jobs run in a daemon thread inside the gunicorn worker, so restarting loses them and their rows sit at "processing" indefinitely. bin/vald-manage reconcile_stuck_requests marks those failed; it leaves a merely slow job alone, using twice the job timeout as the cutoff. Better to deploy when nothing is in flight — the Requests list shows what is, and the queue counter is at the top of it.
Editing secrets.txt needs a restart, not a reload
systemd reads EnvironmentFile= at process start.
Staff logins are not managed from here
The two "Users" in this admin were never the same thing: the accounts on this site are vald.models.User, while the login that opened /admin/ is django.contrib.auth's, an unrelated table. There is one shared staff login and no page for it — the auth models are unregistered in vald_web/urls.py, precisely so the two never sit side by side under the same label again. Change password in the header still works. Adding a staff login, or resetting a forgotten one, is a shell job: bin/vald-manage createsuperuser or bin/vald-manage changepassword admin. Nothing on the public site can grant it — VALD login never touches is_staff.
