Approval always comes before activation, never the other way round. Both routes that can set a password — the activation link and the reset link — refuse an account with is_active off, so an unapproved registrant cannot let themselves in by asking for a password reset.

Actions on the user list

The same four actions appear in the changelist dropdown and, where they would have an effect, as buttons at the bottom of an individual user page.

Approve and send activation email
Sets is_active, issues a fresh activation token, mails the link to the primary address. Skips users who are already active, so it will not re-mail an active account — use Clear password first if that is what you want.
Approve without sending email
Sets is_active only — the same edit as ticking Active on the user page and saving, history entry included. The account then sits in Approved, not activated until the holder tries to log in, which mails them a link. Use when you will tell them by other means.
Clear password (force re-activation)
Drops the password and any pending token. Does not deactivate. The next login attempt on that address mails a fresh activation link. This is the way to recover an account whose holder has lost access to it.
Reject pending registrations
Deletes the selected users, but only those in Pending approval. Active or suspended accounts in the selection are left alone, so this cannot destroy a working account by accident.

To suspend a working account, untick is_active on the user page. The password survives, so re-ticking it restores access with no email round trip.

Links and tokens

Activation and password-reset links share one activation_token field per user, valid for {{ token_max_age_days }} day{{ token_max_age_days|pluralize }} from issue. Issuing a new one invalidates the previous link, and setting a password clears the token so a link cannot be replayed. A user who reports a dead link should simply try to log in again, which issues another.

Where the data lives

This database
Users, preferences, requests, and the live linelist configuration. Snapshotted nightly, tagged with the git revision — a dump only restores against a codebase at a compatible migration state.
VALD3 SVN checkout ($VALD_HOME)
Linelists and the Fortran binaries in bin/. Maintained by the group.
The .cfg files in SVN
Seeded the initial import and are not authoritative any more. Editing them has no effect on the running site; edit the configuration here instead.

Deploying a new version

All of this runs on the server as the vald user, from {{ base_dir }}. Steps 4–5 are only needed when the unit files themselves changed; the rest apply to every deploy.

  1. Snapshot the database first. 
    sudo systemctl start vald-backup.service
    The nightly timer does this too, but a migration is the one thing worth having a fresh snapshot before. Snapshots are tagged with the git revision, because a dump only restores against a codebase at a compatible migration state. Start the unit, not scripts/backup_db.sh directly: the script defaults to backups/ inside the checkout, while the unit sets VALD_BACKUP_DIR to where the nightly snapshots actually go. Running the script bare puts the one snapshot you care about somewhere you will not look for it.
  2. Pull the code, and sync dependencies if they changed. 
    git pull
uv sync
    Dependencies are pinned in uv.lock; uv sync makes .venv match it exactly.
  3. Apply migrations. 
    bin/vald-manage migrate
    Use bin/vald-manage, not python manage.py. manage.py defaults to the development settings module, whose VALD_HOME and result directory point somewhere else entirely; the wrapper reads secrets.txt and sets DJANGO_SETTINGS_MODULE=vald_web.settings_deploy. This instance is running {{ settings_module }}.
  4. If any unit file changed, copy it into place: 
    sudo cp {% for name in unit_files %}{{ name }} {% endfor %}/etc/systemd/system/
  5. ...and reload systemd, which is what makes a changed unit file take effect. Restarting alone will not. 
    sudo systemctl daemon-reload
  6. Restart the application. 
    sudo systemctl restart vald
  7. Check it came back. 
    systemctl status vald
journalctl -u vald -n 50

First-time setup only, to arm the scheduled jobs: 

sudo systemctl enable --now vald-cleanup.timer vald-backup.timer
Verify with systemctl list-timers 'vald*'.

Things that surprise people

There is no collectstatic step
Static files are served by the reverse proxy directly from the checkout. STATIC_ROOT is declared but unused.
Some deploys sign everyone out
Sessions are revalidated against the database on every request, so a change to how they are keyed invalidates existing ones. Changing VALD_URL_PREFIX does the same, because the session and CSRF cookie paths derive from it. Harmless, but expect the support email.
A restart kills running extractions
Jobs run in a daemon thread inside the gunicorn worker, so restarting loses them and their rows sit at "processing" indefinitely. bin/vald-manage reconcile_stuck_requests marks those failed; it leaves a merely slow job alone, using twice the job timeout as the cutoff. Better to deploy when nothing is in flight — the Requests list shows what is, and the queue counter is at the top of it.
Editing secrets.txt needs a restart, not a reload
systemd reads EnvironmentFile= at process start.
