Approval always comes before activation, never the other way round. Both routes that can set a password — the activation link and the reset link — refuse an account with is_active off, so an unapproved registrant cannot let themselves in by asking for a password reset.

Actions on the user list

The same four actions appear in the changelist dropdown and, where they would have an effect, as buttons at the bottom of an individual user page.

Approve and send activation email
Sets is_active, issues a fresh activation token, mails the link to the primary address. Skips users who are already active, so it will not re-mail an active account — use Clear password first if that is what you want.
Approve without sending email
Sets is_active only — the same edit as ticking Active on the user page and saving, history entry included. The account then sits in Approved, not activated until the holder tries to log in, which mails them a link. Use when you will tell them by other means.
Clear password (force re-activation)
Drops the password and any pending token. Does not deactivate. The next login attempt on that address mails a fresh activation link. This is the way to recover an account whose holder has lost access to it.
Reject pending registrations
Deletes the selected users, but only those in Pending approval. Active or suspended accounts in the selection are left alone, so this cannot destroy a working account by accident.

To suspend a working account, untick is_active on the user page. The password survives, so re-ticking it restores access with no email round trip.

Links and tokens

Activation and password-reset links share one activation_token field per user, valid for {{ token_max_age_days }} day{{ token_max_age_days|pluralize }} from issue. Issuing a new one invalidates the previous link, and setting a password clears the token so a link cannot be replayed. A user who reports a dead link should simply try to log in again, which issues another.
